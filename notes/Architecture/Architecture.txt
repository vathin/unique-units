# Архитектура игрового кода

Эта записка описывает, как расширять игру. Авторитетное состояние партии находится в `GameState`; правила не читают `Field`, объекты, спрайты, UI или `global`.

## Новая фигура

1. Создать `XxxBehaviour` от `FigureBehaviour` в `scripts/FigureBehaviour` либо в отдельном скрипте фигуры.
2. Задать как минимум `index`, `sprite`, `card`, `logo`, `rarity`, `deck_class`, `max_deck_amount`, `move_effect_id` и, при наличии способности, `ability_effect_id`.
3. Зарегистрировать экземпляр в `Behaviours.behaviour_list`. Чтобы фигура была видна в декбилдинге, добавить её ключ в `Behaviours.figure_list` и оставить `dev = false`.
4. Если фигура ещё не реализована, использовать `DevFigureBehaviour`: ключ и класс уже известны UI, но фигура скрыта из декбилдинга.
5. Создать или назначить эффекты передвижения и способности. Нельзя реализовывать правило в `Figure`, `Field`, `O_BoardDraw` или обработчике кнопки.
6. Добавить сценарии в `GameplayRulesTests` для доступных целей, отказа на неверном input и результата эффекта.

Пример поведения:

```gml
function RiderBehaviour() : FigureBehaviour() constructor {
    index = "rider";
    sprite = S_Rider;
    card = S_rider_card;
    logo = S_RiderLogo;
    rarity = 1;
    deck_class = "D";
    max_deck_amount = 5;
    move_effect_id = "rider_move";
    ability_effect_id = "rider_ability";
}
```

Карточка в `GameState` хранит только данные:

```gml
{figure_id: "17", behaviour: "rider", owner_id: 1, status: "active"}
```

Не добавлять в неё ссылки на инстансы, `Field`, спрайты, closures UI или контроллеры анимаций.

## Новый эффект или действие

Эффект наследуется от `GameEffect` и регистрируется в `GameRules.effects` под стабильным строковым идентификатором. Он реализует три обязательные части:

- `get_inputs(state, actor_id, partial_inputs)` возвращает следующий требуемый ввод;
- `validate_inputs(state, actor_id, inputs)` повторно проверяет полный набор вводов;
- `execute(state, actor_id, inputs)` клонирует состояние, меняет только клон и возвращает результат.

Шаблон:

```gml
function RiderAbilityEffect() : GameEffect("rider_ability") constructor {
    get_inputs = function(_state, _actor_id, _partial = {}) {
        var _source = GameInput.cell("source_cell", "game.input.rider_source", get_sources(_state, _actor_id));
        if !variable_struct_exists(_partial, "source_cell")
            || !GameInput.has_cell(_source, _partial.source_cell) {
            return [_source];
        }
        return [_source, GameInput.cell("target_cell", "game.input.rider_target",
            get_targets(_state, _actor_id, _partial.source_cell))];
    }

    validate_inputs = function(_state, _actor_id, _inputs) {
        var _specs = get_inputs(_state, _actor_id, _inputs);
        if array_length(_specs) != 2 || !GameInput.has_cell(_specs[1], _inputs.target_cell) {
            return {ok: false, error: "Invalid rider target"};
        }
        return {ok: true, error: ""};
    }

    execute = function(_state, _actor_id, _inputs) {
        var _check = validate_inputs(_state, _actor_id, _inputs);
        if !_check.ok {
            return {ok: false, error: _check.error, next_state: _state, animation_batches: [], events: []};
        }
        var _next = _state.clone();
        // Менять только _next.
        return {ok: true, error: "", next_state: _next,
            animation_batches: [], events: []};
    }
}
```

`execute` не вызывает `O_BoardDraw`, `GameStatePresenter`, `Field`, сетевые методы и не создаёт инстансы. Благодаря этому один и тот же код работает у игрока, бота, хоста и в тестах.

## Inputs и подсветка

Использовать только фабрики `GameInput`:

```gml
GameInput.cell("target_cell", "game.input.rider_target", [[2, 3], [3, 3]])
GameInput.choice("mode", "game.input.rider_mode", [{id: 0, behaviour: "archer"}])
```

Для проверки использовать `GameInput.has_cell` и `GameInput.has_choice`, а не повторять условие другим кодом. `EffectInputController` получает спецификации через `GameRules.get_inputs`, сам подсвечивает `allowed_cells` и передаёт выбранные значения в `EffectAction`. Поэтому допустимые клетки на экране и в `validate_inputs` всегда должны происходить из одного `get_inputs`.

Если эффект отменяем только до определённого момента, переопределить `is_cancelable(state, actor_id, partial_inputs, progress)`. `progress` хранит только факты UI, например уже показанную карточку; игровые правила не должны зависеть от UI.

## Новые визуальные события и анимации

Логический эффект возвращает `animation_batches`: внешний массив выполняется последовательно, вложенный - одновременно.

```gml
animation_batches: [
    [{type: "move", figure_id: _id, from: [1, 2], to: [2, 3], duration_frames: 12}],
    [{type: "hit", figure_id: _id, at: [2, 3], duration_frames: 8}]
]
```

Для нового типа события:

1. Добавить сериализуемые поля события в `execute` эффекта. Указывать координаты и `figure_id`, когда событие относится к фигуре.
2. Обработать `event.type` в `GameStatePresenter.play_batch`.
3. Создать или переиспользовать controller анимации из `scripts/*AnimationController`.
4. Если во время анимации требуется временно изменить только отображение, сохранить это как `pending_visual_updates`. Не менять `Game.game_state` и не вызывать правила.
5. После завершения всех пакетов presenter сам вызывает `apply_state(pending_state)`. Новое подтверждённое состояние не должно применяться раньше окончания анимаций.
6. Добавить тест правила на форму события, а ручной тест - на порядок и длительность анимации.

`GameStatePresenter` - единственная точка, где логические события превращаются в `Field`, `Figure` и контроллеры анимации.

## Подключение к UI, боту и сети

Для обычной фигуры `FigureActionController` получает идентификаторы эффектов из `Behaviours` и открывает `EffectInputController`. Специальный UI допустим только как адаптер: он собирает input и создаёт `EffectAction`, но не решает, разрешено ли действие.

Бот получает те же спецификации и исполняет эффект на клоне `GameState`. При добавлении эффекта нужно убедиться, что `GameLoopController.get_legal_action_descriptors` может построить для него полный набор inputs; отдельный бот-код для правил не нужен.

В онлайн-матче клиент посылает intent `{effect_id, inputs, base_revision}`. Хост валидирует и выполняет эффект, затем рассылает новое состояние и `animation_batches`. Не передавать по сети ссылки на объекты, `Field`, инстансы или функции.

## Проверка перед завершением

- Фигура зарегистрирована, имеет корректные спрайты и правила колоды.
- `get_inputs` не предлагает клеток, которые `validate_inputs` отвергает.
- Неверные координаты, чужая фигура и неактивный ход возвращают `{ok: false}` без изменения исходного state.
- `execute` не читает и не меняет UI.
- События анимаций состоят только из сериализуемых данных.
- Сценарии добавлены в `GameplayRulesTests`; отдельно проверены локальная игра, бот и HTML5.
